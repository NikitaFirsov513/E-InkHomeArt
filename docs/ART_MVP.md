# Art MVP: фотография по Wi-Fi и постоянное хранение

19.11.2026. Реализована программная цепочка этапов 3–4: браузер готовит
PNG/JPEG, устройство принимает готовый кадр, проверяет его, сохраняет во Flash,
показывает четыре уровня серого и восстанавливает картину при старте.
Проверки на ПК и сборка не заменяют приёмку радио/Flash/изображения на плате.

## Первый запуск

Для ESP32-S3-WROOM-1U нужна подключённая внешняя антенна 2,4 ГГц.
Использовать уже проверенное питание прототипа: ток Wi-Fi надо проверить на плате.

Настройки VS Code теперь выбирают `build/art`, `sdkconfig.art` и соответствующий
ELF. В терминале ESP-IDF 6.1, из корня проекта:

```powershell
idf.py -B build/art -D SDKCONFIG=sdkconfig.art -D 'SDKCONFIG_DEFAULTS=sdkconfig.defaults;sdkconfig.defaults.art' build
idf.py -B build/art -p COM7 flash monitor
```

При первом переходе на Art нужен полный `flash`, включая таблицу разделов,
а не только `app-flash`. `erase-flash` не требуется.

В UART на 115200 будут строки:

```text
ART_APP: Wi-Fi SSID: EInkHomeArt-XXXXXX
ART_APP: Wi-Fi: open network, no password
ART_APP: Photo page: http://192.168.4.1 (stay connected without Internet)
```

SSID содержит часть MAC; сеть открытая, пароль не требуется.
Повторить эти строки: `?` и Enter в UART.
При ошибках NVS прошивка сообщает ошибку, не стирает NVS автоматически.

1. Подключиться с телефона/ПК к этой сети без пароля.
2. Согласиться остаться в сети **без Интернета**. При необходимости отключить
   автоматическое переключение телефона на другую сеть.
3. Открыть **http://192.168.4.1** в браузере. Страница находится на ESP32,
   локальная копия `file:///.../index.html` отправлять на устройство не будет.
4. Выбрать PNG/JPEG, настроить композицию, яркость, контраст и полутоновый узор.
5. Нажать **«Показать на устройстве»**. Исходник остаётся в браузере;
   ESP32 получает 96064 байта: заголовок и готовые 96000 байт пикселей.

На пустом устройстве первая загрузка может обновить экран сразу. При старте
калибровочные полосы не рисуются; до первой загрузки E-Ink сохраняет прежнее
изображение. Это нормально и не означает, что осталась старая прошивка.

## Сохранено и показано — разные состояния

HTTP подтверждает сохранение только после двух CRC, записи, чтения обратно
и финального commit. Затем отдельная задача читает сохранённый кадр и обновляет
панель. Страница показывает сохранение, начало обновления и результат.
Повреждённый пакет или обрыв передачи до сохранения не заменяет картину.

Ручная загрузка фото запускает обновление сразу после сохранения, без
трёхминутного таймера. После завершения одного refresh можно отправить следующее
фото. Передача, ожидание BUSY и выключение панели выполняются последовательно;
изменить активный буфер во время refresh нельзя. Автоматического слайд-шоу нет.
Сохранённые варианты не образуют галерею.

Таймер 180 с был консервативной политикой приложения, удалённой для ручной
смены фото. [FAQ Good Display](https://www.good-display.com/faq/1/) указывает
180 с в разделе о трёхцветных панелях; этот раздел сам по себе не задаёт
обязательную блокировку для нашей GDEY075T7 с четырьмя уровнями серого.
Изменение не ускоряет заводскую waveform. Ресурс при непрерывных частых
полных refresh отдельно не измерен; автоматический непрерывный режим не добавлен.

Во время SPI/BUSY буфер занят; отправка получает 409, страница предлагает
повторить после обновления. Статусы HTTP, тач и D6 продолжают работать.
После ошибки панели нет автоматического бесконечного цикла refresh;
повторная отправка ставит сохранённый кадр в очередь новой попытки.

Статус «передана на экран» означает завершение SPI, BUSY и выключения панели.
Правильные оттенки и физическую картинку нужно проверить глазами.

## Flash и сохранение при обновлении прошивки

[partitions.art.csv](../partitions.art.csv):

| Раздел | Адрес | Размер | Назначение |
|---|---|---|---|
| nvs | 0x9000 | 24 КиБ | Данные SDK; старые адрес/размер сохранены |
| phy_init | 0xF000 | 4 КиБ | Данные PHY; прежний адрес |
| factory | 0x10000 | 2 МиБ | Приложение; прежний адрес, увеличенный резерв |
| art | 0x210000 | 256 КиБ | Только подготовленный кадр; data subtype 0x40 |

ArtStore использует два слота по 128 КиБ: текущую картину и резерв для
восстановления после прерванной записи. Неактивный слот стирается при замене,
новый commit записывается последним. При старте оба слота проверяются по CRC.
По договорённости хранится готовое изображение, исходного JPEG/PNG на плате нет.

Обычный `flash` этой прошивки содержит bootloader, таблицу и приложение;
образа для art-раздела в `flasher_args.json` нет. Обычное обновление с этой же
разметкой сохраняет картину. `erase-flash`, стирание art-раздела или другая
разметка с пересекающимися разделами могут её удалить. OTA ещё не реализована.

## Реализация

- `ArtManager` — один владелец ArtStore и панели, один буфер 96064 байта,
  отдельная задача отображения. Буфер выделяется во внутренней RAM до Wi-Fi;
  PSRAM по-прежнему выключена. Мьютекс исключает запись в передаваемый кадр.
- Во время приёма HTTP сохраняет данные только в RAM. При неверном заголовке,
  размере, CRC или тайм-ауте до commit Flash не обновляется. Лимит передачи —
  30 с, чтение небольшими блоками. Отклонённые POST закрывают соединение.
- `GET /api/status` — состояние хранилища, сохранённое/показанное поколения,
  результат обновления. Совместимое поле `refresh_wait_seconds` равно 0.
  Успешная запись сама по себе
  не повышает `displayed_generation`.
- `POST /api/image` — ровно 96064 байта `application/octet-stream`,
  заголовок `X-Art-Upload: 1`; HTTP 202 только после успешного сохранения.
  CORS не разрешается. Заголовок требуется и для защиты от сторонних форм.
- Статические HTML/CSS/JS встроены в приложение, без CDN и внешних сервисов.
- SoftAP — открытая сеть без пароля по выбору пользователя, 2,4 ГГц,
  максимум два клиента. Wi-Fi в этом MVP остаётся
  включённым для загрузки. Автоматическое выключение радио, сон ESP32,
  настройка домашней сети и OAuth относятся к дальнейшим этапам.
- Активны панель, GT911, UART0, D6 и радио. ADC, LIS2DW12, управление зарядником
  и внешняя PSRAM не запускаются. Тач пока выдаёт координаты, домашнего UI нет.

## Проверки

```powershell
node tools/check_art_client.js
node tools/check_art_upload.js
python tools/check_art_http.py
python tools/check_drivers.py --optimization O2 --build build/host-review-o2
python tools/check_art_frame.py
```

Нативный тест запускает **реальные** `art_http.c`, `art_manager.c`, ArtStore
и кодек с имитированными SDK/Flash/RTOS/панелью. Проверяются фрагментированная
передача, размер, CRC, обрыв, тайм-аут, недоступность/занятость, ошибки записи,
восстановление при старте, владение буфером, поколения, повторные фото без
искусственной паузы и восстановление после ошибки.
Это последовательная симуляция границ задач, не нагрузочное испытание FreeRTOS
на двух ядрах. JS-тесты исполняют настоящие контроллеры страницы и кодек,
подменяя браузер/сеть. 19.11.2026 все перечисленные проверки прошли, включая
20 сценариев драйверов, совместимость JavaScript/C, HTTP и ArtManager.
ESP-IDF 6.1 собрал основной Art и сохранённый Art Gray; основной образ
помещается в разделе 2 МиБ. Пересборка с открытой сетью также прошла.
Проверено, что flash manifest
не содержит записи art-раздела. 19.11.2026 образ без ручной задержки записан
на плату через COM7 после ручного BOOT+RESET; esptool подтвердил хеш данных.
Art-раздел не записывался. Проверка второй загрузки через страницу ещё нужна.
На плате ещё нужно подтвердить:

1. Подключение к AP и открытие страницы с телефона/ПК.
2. Загрузку фотографии, все четыре оттенка, время и свободную память из UART.
3. Полное отключение питания и восстановление той же картины (`STORE RESTORED`).
4. Обрыв загрузки и последующее восстановление предыдущей целой картины.
5. Замену фото и обычное обновление прошивки с сохранением картины.
