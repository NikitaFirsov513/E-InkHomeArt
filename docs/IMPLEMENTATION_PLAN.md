# E-Ink Home Art: этапы основной прошивки

Основание — [исходное ТЗ Revision 1](../design/ui-rev1/reference-tz-rev1.md).
Это план реализации. Пункты, требующие проверки на плате, не считаются
выполненными по результату одной программной сборки.

## Согласованные решения — 19.11.2026

- Art Mode — **четыре уровня серого** для фотографий.
- Пользователь выбирает обычный **PNG/JPEG** на телефоне или компьютере.
- Декодирование, кадрирование, масштабирование и перевод в градации выполняет
  **клиент в браузере**, не ESP32.
- На устройство отправляется и сохраняется **готовый кадр**, исходный PNG/JPEG
  не хранится. Это явный выбор пользователя после обсуждения двух вариантов.
- Размер изображения — 800×480×2 бита = **96000 байт**. С заголовком проверки
  передаётся 96064 байта. Это 96 КБ в десятичной записи, около 93,75 КиБ пикселей.
- Картина должна переживать отключение питания и восстанавливаться из Flash.
- Загрузка фотографии не требует компиляции или перепрошивки приложения.

## План с проверяемым результатом каждого этапа

| Этап | Работа | Когда этап завершён |
|---|---|---|
| **1. Формат, клиент и модуль хранения** | Общий двухбитный формат, CRC, обработка PNG/JPEG в браузере, два слота постоянного хранения, адаптер ESP-IDF | Клиент и C-код согласуются побайтово; повреждённые кадры отвергаются; имитация прерывания записи восстанавливает последний целый кадр. **Программная основа готова**, браузерное взаимодействие и физическая Flash требуют дальнейшей проверки |
| **2. Art Mode: четыре градации на панели** | Отдельный API UC8179 для 4 gray по модельному примеру производителя; полосы четырёх уровней, затем подготовленная фотография | **Драйвер и отдельный профиль проверки реализованы**, см. [ART_GRAY_TEST.md](ART_GRAY_TEST.md). Завершение этапа: на физическом экране различимы все четыре уровня, порядок и полярность верны, BUSY завершается, нет критических артефактов |
| **3. Постоянная картина на устройстве** | Новый основной профиль, выделенный art-раздел, `ArtManager`, загрузка сохранённого кадра при старте | **Программная цепочка реализована и проверена на имитации Flash/RTOS**, см. [ART_MVP.md](ART_MVP.md). На плате: записать картину, полностью выключить питание, включить: загружается тот же кадр. Неполная новая запись не уничтожает предыдущую |
| **4. Загрузка по Wi-Fi** | ESP32 отдаёт клиент подготовки; приём готового кадра, проверка, сохранение, очередь отображения и статусы | **HTTP, SoftAP и клиент реализованы, обработчики протестированы на ПК**. Пользователь выбрал точку доступа устройства для первого запуска. На плате: PNG/JPEG → preview → отправка → картина на E-Ink → сохранность после перезапуска; экспорт `.ehart` больше не нужен |
| **5. Art ↔ Smart Home UI** | Кириллический UI, комнаты/устройства/сценарии, события тача, возврат к той же картине через 30–60 с | Навигация работает на панели; первое касание не вызывает случайную команду; тач и UART не блокируются обновлением |
| **6. Яндекс Дом** | Wi-Fi-настройки, официальный OAuth/API, устройства и состояния, команды, ожидание/ошибки/отсутствие сети | Хотя бы одно настоящее устройство управляется, состояние не подменяется выдуманным успехом. Home Assistant остаётся отдельным следующим этапом |
| **7. Сон, пробуждение и аккумулятор** | GT911/INT, PowerManager, отключение Wi-Fi/индикации, измерение токов, заряд/низкий заряд и весь пользовательский цикл | Проверены реальные wake, потребление, питание и восстановление. После этого количественно согласовать время входа и автономность |

Работа ведётся в таком порядке, чтобы сначала получить полезный вертикальный
сценарий с настоящей фотографией, а затем добавлять управление домом. Параметры
сна можно исследовать параллельно с Art Mode, но низкое потребление не будет
объявлено готовым раньше аппаратных измерений.

## Что уже сделано на первом этапе

- [Клиент подготовки](../web/art/index.html): выбор PNG/JPEG, композиция
  «заполнить экран» / «поместить целиком», смещение, яркость, контраст,
  опциональный Floyd–Steinberg для четырёх уровней, точный пиксельный preview.
- [Описание формата](ART_FRAME_FORMAT.md) и компонент `art_frame` на C:
  проверка сигнатуры, версии, геометрии, порядка битов, длины и двух CRC.
- `art_store`: один текущий кадр и предыдущий целый кадр в двух Flash-слотах.
  Новая запись проверяется чтением обратно, commit записывается последним.
- ESP-IDF-адаптер использует только отдельный data-раздел с subtype `0x40`;
  он не форматирует файловую систему и не принимает разделы NVS/SPIFFS по имени.
- Компоненты изначально проверялись в `build/art-foundation`; теперь
  [основной профиль Art](ART_MVP.md) в `build/art` подключает ArtStore,
  выделенный раздел и браузерную загрузку. Диагностические профили сохранены.

**Это Art MVP с незавершённой аппаратной приёмкой:** 4-gray API UC8179,
[профиль проверки](ART_GRAY_TEST.md), сетевой приём и art-раздел реализованы;
радио, восстановление после питания и пользовательский цикл ещё проверяются
на плате по [инструкции](ART_MVP.md). Существующий Display/Touch V6
не умеет отображать этот двухбитный формат: нельзя передавать его в старый
`uc8179_display_frame()`, который ожидает 48000 байт монохромных данных.

## Как попробовать первый клиент

Открыть [web/art/index.html](../web/art/index.html) обычным браузером. Страница
работает с локальным файлом, без CDN и облачной обработки. Для проверки доступны
экспорт подготовленного `.ehart` и preview PNG. Это временные инструменты этапа 1,
не обязательные действия пользователя основного Art-профиля: в нём открывают
страницу самого устройства и нажимают «Показать на устройстве».

При необходимости запустить из корня проекта:

```powershell
python -m http.server 8000 --bind 127.0.0.1 --directory web/art
```

Затем открыть `http://127.0.0.1:8000/`. Это подготовка/экспорт, не страница ESP32.
Контроллеры проверены с имитированными границами DOM/canvas/сети; обработка
пикселей и кодек настоящие. Проверка страницы на устройстве ещё предстоит.

## Контракт загрузки

Реализованный поток основного профиля: **локальный PNG/JPEG → preview 4 gray → готовый пакет →
проверка → запись во Flash → чтение обратно → commit → очередь отображения**.

ESP32 не должен принимать JPEG/PNG за правильный подготовленный кадр, молча
обрезать файл или подтверждать успех до окончания проверки и сохранения.
Успешное сохранение и успешный refresh — разные события: страница отдельно
показывает «сохранено» и состояние обновления экрана. При обрыве HTTP активный кадр
не заменяется. Сервер/драйвер/Flash вызываются сериализованно, не из ISR.

В первом MVP хранится одна выбранная картина; второй слот — резерв для
восстановления, не полноценная галерея. Для двух слотов нужно **256 КиБ**:
по 128 КиБ на слот, включая заголовки, выравнивание и резерв. Основной профиль
выделяет их с адреса 0x210000 в `partitions.art.csv`. 19.11.2026 приложение
без задержки ручной смены фото записано через COM7 с проверкой хеша;
art-раздел при этой прошивке не затрагивался.

Обновление приложения должно сохранять art-раздел. Полное `erase-flash`
удаляет и картину: это не обычное обновление приложения.

## Решения, которые ещё не утверждены

- Вариант основного интерфейса A/B/C и точный состав быстрых действий.
- Конкретный тайм-аут внутри 30–60 с и точность шаговых регуляторов.
- Способ настройки домашней сети и OAuth. Для первого запуска загрузки уже
  согласована открытая точка доступа устройства без пароля.
- Целевые холодный отклик и автономность, политика очистки и поведение сна.
- Галерея, загрузка исходников, Reader Mode, HA, dock — не добавляются автоматически.

Четыре уровня серого **уже выбраны**, повторно предлагать для Art Mode только
двухцветную картинку как окончательное решение не нужно.

## Проверки

```powershell
node tools/check_art_client.js
node tools/check_art_upload.js
python tools/check_art_http.py
python tools/check_drivers.py --optimization O2 --build build/host-review-o2
python tools/check_art_frame.py
```

Проверяются четыре допустимых уровня, упаковка пикселей, прозрачность,
повторяемый dithering, CRC, некорректные пакеты, геометрия cover/contain,
обработка ошибки файла, совместимость JavaScript/C, перезапуск хранилища,
прерванные записи до commit/во время commit и возврат к предыдущей целой записи.

Сверено с первичными источниками:
[характеристики GDEY075T7-T01](https://www.good-display.com/product/483.html),
[ESP-IDF Partition Tables](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s3/api-guides/partition-tables.html),
[ESP-IDF HTTP Server](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s3/api-reference/protocols/esp_http_server.html).
