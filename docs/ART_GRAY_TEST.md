# Этап 2: четыре уровня серого на GDEY075T7-T01

19.11.2026. Это отдельный профиль проверки панели перед подключением ArtManager
и сетевой загрузки. Текущий Display/Touch V6 сохраняется в своей сборке.
Разметка Flash не меняется; ArtStore в этом профиле не вызывается.
Основной профиль VS Code теперь — [Art MVP](ART_MVP.md) в `build/art`.
Для возврата к этому тесту использовать явные команды с `-B build/art-gray`
ниже: он сохранён отдельно от приложения загрузки и хранения.

## Что проверяем

При старте выводится один калибровочный кадр 800×480. Верхняя половина:
**чёрный → тёмно-серый → светло-серый → белый**, четыре полосы по 200 пикселей.
Нижняя половина имеет обратный порядок. Нужно увидеть четыре различных уровня,
без повторения/обрезания второй половины изображения.

Используется модельный заводской OTP-режим Good Display. Это полный серый refresh,
его время измеряется отдельно; скорость быстрого монохромного partial сюда не
переносится. После BUSY вызывается power off и deep sleep. Автоматических
повторных обновлений нет. Между ручными полными обновлениями выдерживается
180 секунд от начала предыдущей попытки; RESET начинает новую тестовую сессию,
поэтому не следует использовать его для частого повторения картинки.

D6 мигает независимо. GT911 опрашивается основной задачей: в UART идут `TOUCH`
с координатами, касание не запускает refresh. Радио, PSRAM, ADC, зарядник и
акселерометр не запускаются. SPI — 8 МГц, тайм-аут BUSY — 20 секунд.

## Сборка и запуск

В терминале с ESP-IDF 6.1, из корня проекта:

```powershell
idf.py -B build/art-gray -D SDKCONFIG=sdkconfig.art-gray -D 'SDKCONFIG_DEFAULTS=sdkconfig.defaults;sdkconfig.defaults.art-gray' build
idf.py -B build/art-gray -p COM7 flash monitor
```

Порт при необходимости заменить. `erase-flash` не нужен. Эти команды используют
свой каталог сборки и конфиг; обычный `build/` остаётся профилем Display/Touch.

Команды UART, один символ и Enter:

| Команда | Действие |
|---|---|
| `g` | Повторить калибровочные полосы |
| `p` | Показать встроенный подготовленный кадр, если он добавлен при сборке |
| `?` | Помощь |

Запрос во время паузы ожидает разрешённого времени; новый запрос заменяет
ожидающий. Текущий буфер передачи не меняется. При ошибке нет автоматического
повторного refresh: сначала смотрим лог. Нормальное окончание:

```text
ART_GRAY: GRAY4 transfer + BUSY + shutdown: READY
```

`PERF` показывает передачу **96000 байт** в две плоскости, время питания,
передачи, BUSY и всей операции. Успех SPI/BUSY не доказывает правильность оттенков:
проверка физического изображения обязательна.

## Проверка подготовленной фотографии

Открыть [клиент подготовки](../web/art/index.html), выбрать свой PNG/JPEG,
отрегулировать композицию и скачать `.ehart`. Временно встроить этот пакет:

```powershell
idf.py -B build/art-gray -D SDKCONFIG=sdkconfig.art-gray -D 'SDKCONFIG_DEFAULTS=sdkconfig.defaults;sdkconfig.defaults.art-gray' -D 'ART_TEST_FRAME=D:/path/to/picture.ehart' build
idf.py -B build/art-gray -p COM7 flash monitor
```

При старте по-прежнему показаны полосы. `Embedded photo: validated` подтверждает
заголовок, размер, геометрию и обе CRC. Затем команда `p` ставит фото в очередь.
Неверный пакет не показывается, калибровка остаётся доступна. Для удаления
встроенной фотографии пересобрать с `-D ART_TEST_FRAME=`.

Встраивание в образ — временный способ проверки драйвера на этапе 2.
Согласованный пользовательский сценарий остаётся прежним: выбор PNG/JPEG в
браузере → обработка клиентом → передача готового кадра по Wi-Fi → постоянное
хранение без перепрошивки. Это реализуется этапами 3–4.

## API, преобразование и источник

- `uc8179_init_gray4()` сбрасывает панель и выбирает OTP четыре градации.
- `uc8179_display_gray4()` принимает **только 96000 байт пикселей**, без 64-байтного
  заголовка `.ehart`. Порядок: четыре пикселя на байт, старшая пара бит первой,
  0 = чёрный, 1 = тёмно-серый, 2 = светло-серый, 3 = белый.
- OLD RAM (0x10) = инвертированный младший бит каждого уровня; NEW RAM (0x13)
  = инвертированный старший бит. Ровно 48000 байт в каждую плоскость.
- Преобразование выполняется в существующем DMA-буфере до 4096 байт, без двух
  дополнительных кадров в RAM. Исходник может находиться в Flash/PSRAM.
- Монохромные и серые API не смешиваются в одной инициализации. Для смены
  режима нужен соответствующий `init`; серый кадр не является базой partial.
- После ошибки передачи/refresh требуется новая инициализация. Все вызовы
  панели выполняются последовательно в одной задаче.

Источник: [официальный Good Display EPD.cpp, фиксированный commit d5ed3b7](https://github.com/gooddisplayshare/ESP32epdx/blob/d5ed3b777bedb9b407ccff09dc810a9248eb7926/examples/2-Colors%20(BW)/7.5/GDEY075T7/EPD.cpp),
функции `EPD_Init_4G`, `EPD_WhiteScreen_ALL_4G`, `Display_4Level_Gray`.
Сверены PSR=0x1F, CDI=0x10/0x07, booster=0x27/0x27/0x18/0x17,
TSFIX=0x02 и TSSET=0x5F. Собственные LUT и произвольные параметры драйва
не используются. Длинная пауза reset сохраняет уже проверенные тайминги драйвера.

В `EPD_WhiteScreen_ALL_4G` у производителя NEW-цикл имеет границу `48000*2`,
хотя за одну итерацию читает два байта исходника. Для 96000-байтного кадра это
выход за пределы. В нашей реализации обе плоскости ограничены 48000 байтами.

Проверки на ПК покрывают все 256 комбинаций входного байта, каждый пиксель
обеих плоскостей, последний пиксель, размеры пакета, ограничение DMA-блока,
несовместимые режимы, сбои SPI и тайм-аут BUSY при обновлении.
19.11.2026 прошли все 20 сценариев `check_drivers.py --optimization O2`.

кодека и прежний Display/Touch. Финальный `build/art-gray` — только калибровка,
`build/` — прежний Display/Touch. Плата агентом не прошивалась;
физические оттенки и фото пока требуют проверки на собранной плате.
