# Разбор ТЗ и пригодности текущего дисплея

**Статус: предложение к обсуждению. Исходное ТЗ сохранено без правок.**

**Решение пользователя от 19.11.2026:** Art Mode делаем в четырёх уровнях серого;
PNG/JPEG обрабатывается в браузере, устройство хранит только готовый двухбитный
кадр. Прежнее предложение начать окончательный Art Mode с 1 bpp не принято.
Дальнейшая реализация описана в [плане](../../docs/IMPLEMENTATION_PLAN.md).

Основание — пользовательский `eink_home_art_TZ_rev1.md`, Revision 1, и текущая
прошивка Display/Touch V6. Это анализ E-InkHomeArt на ESP32-S3, а не перенос
требований другого проекта `home_panel` на ESP32-P4 с LCD.

## Вывод

**Скорости панели достаточно для пользовательских сценариев этого ТЗ:** картина
в ожидании, эпизодическое управление комнатами/устройствами, запуск сценариев,
дискретная настройка параметров и возврат к картине. Непрерывная анимация,
перетаскивание и плавная прокрутка для MVP не нужны.

Это заключение о пригодности сценариев, а не подтверждение готовности всего
устройства. Критические ещё не проверенные части — холодное пробуждение,
питание GT911 в ожидании, Wi-Fi/OAuth, потребление и аккумуляторный тракт.

## Что ТЗ действительно требует

| Требование | Оценка / решение для макетов |
|---|---|
| §1, §2.1, §6.1: большую часть времени картина, без постоянных органов управления | Отдельный полноэкранный Art Mode; на нём нет часов, Wi-Fi, батарейки, меню или подсказки касания |
| §2.2: касание открывает управление | Первое касание предлагается использовать только для пробуждения; команду устройству отправляет следующее осознанное действие |
| §2.2, §5.2: возврат через 30–60 с | Предлагается 45 с от последнего пользовательского действия, не от последнего сетевого опроса |
| §6.2: устройства, комнаты, сценарии, состояния | В A шесть быстрых действий; B показывает группировку по комнатам; раздел сценариев доступен в нижней навигации |
| §6.2: включение, выключение, параметры, запуск сценария | Явные подписанные действия; параметры через шаги / предустановки и «Применить» |
| §6.2: русский язык | Макеты используют кириллические шрифты; в прошивке понадобится реальный кириллический растеризатор/шрифт, текущий диагностический ASCII-шрифт этого не обеспечивает |
| §5.1: Яндекс Дом в MVP | Один провайдер в настройках; интерфейс управления зависит от доступных у конкретного устройства умений |
| §9: HA, Reader Mode, расширенная галерея и dock позднее | В показанный MVP не включаются; схема провайдеров должна допускать HA в будущем |
| §3.1: режимы и уровни серого подтвердить | Макеты реализуемы в текущем двухцветном режиме; четыре уровня серого для Art Mode — отдельная работа и решение пользователя |
| §4, §8, §10: автономность, зарядка, низкий заряд, сон | Рендеры этого не подтверждают; нужны аппаратные измерения и отдельные тесты |

Все имена комнат, устройства, проценты, температура, время и состояния в
рендерах — примеры, а не результат обнаружения настоящего умного дома.

## Реальная скорость: где достаточно, а где есть риск

Из пользовательских логов V4: partial BUSY **372–388 мс**, передача **7–21 мс**,
включение питания **137–144 мс**, выключение около **49 мс**, отрисовка
**99–101 мс**. Полный цикл обновления с подготовкой базы — **4108 мс**.
Это измерения предыдущей версии; V6 оценена пользователем как более быстрая,
но новых количественных PERF-замеров пока нет.

V6 использует CPU 240 МГц, `-O2`, подготовку нового кадра во время BUSY,
прямоугольник изменений и короткие серии без повторного включения питания.
Ограничение между началами попыток — 350 мс; оно не отменяет BUSY. При
неизменном BUSY 0,38 с верхняя оценка — около 2,6 обновления/с, реальная
частота ниже из-за остальных затрат и периодических очисток.

| Сценарий | Пригодность | Предлагаемое поведение |
|---|---|---|
| Включить свет / запустить сценарий | Хорошо | Одна команда на отпускание; затем одно обновление результата, при необходимости статичный статус ожидания |
| Выбрать комнату / страницу | Хорошо для E-Ink | Один завершённый переход без промежуточной анимации; кнопки страниц для длинных списков |
| Настроить яркость / температуру | Хорошо при дискретном управлении | Кнопки шага и предустановки; сеть вызывается по «Применить», а не на каждое промежуточное движение |
| Показать картину, долго не меняя её | Основной подходящий сценарий | Одна передача картинки, завершение обновления и переход к низкому потреблению |
| Быстро проснуться и сразу управлять | **Пока не доказано** | Отдельно измерить пробуждение, первый вывод меню и готовность сети |
| Непрерывное рисование / анимации | Не требуется ТЗ | Не переносить эти ограничения диагностической сетки на оценку всего продукта |

### Основной риск — первый вход из Art Mode

В текущем `uc8179.c` deep sleep / RESET инвалидируют базу partial. Драйвер
разрешает `prepare_partial` только после успешного полного кадра. Поэтому
**просто добавить сон к V6 и обещать меню через 0,38 с нельзя**: после пробуждения
текущая последовательность потребует полного обновления. По старому измерению
это около четырёх секунд, дополнительно могут потребоваться загрузка состояния,
подключение Wi-Fi и HTTPS-запросы.

Панель имеет заявленный fast refresh 1,5 с, но этот режим в нашем драйвере пока
не реализован. Его можно исследовать отдельно как способ смены страницы;
он не заменяет обычную периодическую очистку. Источник:
[характеристики GDEY075T7-T01](https://www.good-display.com/product/483.html).

Быстрый вход и сохранение известной базы без долгого полного цикла требуют
отдельной проверки алгоритма сна/пробуждения и качества картинки. Это не
утверждённое изменение режима панели в текущем предложении.

## Предлагаемая структура экранов

1. **Art Mode** — только выбранное изображение.
2. **Главная A** — четыре частых устройства и два сценария; конкретный состав
   выбирается с пользователем. Название карточки открывает подробности,
   подписанная кнопка выполняет действие. Метки «Включён» и «Выключить»
   намеренно раздельны: состояние и действие не должны путаться.
3. **Комнаты B** — список комнат и устройства выбранной комнаты. Для длинных
   списков в реализации нужны явные страницы вместо инерционной прокрутки.
4. **Устройство** — доступные параметры данного устройства. В примере лампа:
   явные команды питания, текущая яркость, черновое значение, шаг, предустановки
   и применение. Температура, шторы и другие умения получают свой шаблон.
5. **Сценарии** — подписанные крупные кнопки с результатом запуска. Удаление,
   редактирование автоматизаций и сложные конструкторы не добавляются в MVP.
6. **Настройки** — Wi-Fi, подключение Яндекса, тайм-аут и изображение.
7. **Ожидание / нет сети / ошибка** — отдельные состояния, без бесконечных
   анимаций и без ложного сообщения об успешном выполнении.

Вариант C показывает изображение рядом с действиями только во время
**Smart Home Mode**. Он не предлагает постоянное меню поверх картины в Art Mode.
Копия картинки в таком меню не делает весь вход автоматически частичным:
положение/масштаб изображения меняется, а база после сна всё равно требует решения.

## Правила реакции и достоверности

- Первое касание после сна предлагается поглощать до отпускания, чтобы оно
  случайно не активировало кнопку на новом экране.
- Показывать возраст сохранённых состояний, если сеть ещё не обновила данные.
  При отсутствии сети команды в макете недоступны; картина и настройки остаются доступны.
- Использовать явные «Включить» / «Выключить», не вычислять опасный toggle из
  заведомо устаревшего состояния. Поддержка любого действия проверяется по
  умениям конкретного устройства, не по одному его названию.
- Ответ API о приёме команды и подтверждённое новое состояние — разные факты.
  Если команда принята, но устройство ещё не подтвердило состояние, показывать
  соответствующее сообщение, а не придумывать результат.
- Статичное «Отправляем…» выводить при заметном ожидании. Если ответ пришёл
  быстрее очередного обновления, сразу показать результат, не заставляя панель
  отдельно отрисовывать промежуточный кадр. Не перезапускать команду повторными
  касаниями, пока она выполняется.
- Короткие последовательности нажатий объединять в последний нужный кадр.
  Непрерывные спиннеры, секундные часы, пульсации и автопрокрутка не нужны.
- Минимальная высота кнопок в макетах — 44 px, крупные действия 56–72 px.
  Это около 9–15 мм при шаге пикселя панели 0,204 мм. Фактическое удобство и
  попадания по краям нужно проверить на установленном сенсоре.

## Питание, сеть и память

INT GT911 в проекте — GPIO9. ESP32-S3 допускает RTC GPIO0…21 как источник
ext0/ext1 wakeup: со стороны номера пина препятствия нет. Это **не подтверждает**
работу wake: нужно выбрать режим GT911, проверить сохранение его питания,
уровень/длительность INT, подтяжки и отсутствие ложных/повторных пробуждений.
Источник: [ESP-IDF Sleep Modes](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s3/api-reference/system/sleep_modes.html).

Яндекс предоставляет пользовательский API для устройств, групп и сценариев;
нужны OAuth-разрешения `iot:view` / `iot:control`. Это соответствует направлению
ТЗ, но авторизация, обработка истечения токена, TLS и восстановление связи
в этой прошивке ещё не реализованы. Источник:
[официальный протокол Яндекс IoT](https://yandex.ru/dev/dialogs/smart-home/doc/ru/concepts/platform-protocol).

Один кадр 800×480 в 1 bpp — 48000 байт. Текущий конвейер V6 использует три
изображения (два подготовленных и копию показанного), то есть 144000 байт
пикселей плюс модели/стеки. Добавление Wi-Fi, TLS, JSON, кириллицы и декодирования
картин требует новой проверки RAM. В модуле предусмотрено 8 MB PSRAM,
но она сейчас отключена в bring-up профиле; сначала надо её надёжно запустить.

Хранение сотни несжатых монохромных картин потребует 4,8 MB плюс метаданные.
16 MB Flash не означает столько свободной файловой памяти: текущая разметка
содержит factory app 1 MB и пока не выделяет отдельный раздел для графики.
Формат загрузки картин, файловое хранилище, OTA и новую разметку надо спланировать.
MVP может начинаться с одной локальной картины, не с полноценной галереи.

В Art Mode нужно прекращать диагностическое мигание D6, лишний опрос и задачи,
которые мешают сну, завершать refresh перед отключением узлов. Оценка ресурса
аккумулятора по рендерам или паспортному току одного ESP невозможна.
На текущем прототипе испытания зарядки/аккумулятора нельзя считать закрытыми
только потому, что дисплей заработал от лабораторного питания.

В ТЗ указан WROOM-1, а документация платы указывает WROOM-1U-N16R8; это
уточнение обозначения модуля/антенны для будущего согласованного ТЗ.

## Что предлагается согласовать

Это предложения, **не изменения утверждённого ТЗ**:

| Решение | Предложение | Отношение к ТЗ |
|---|---|---|
| Главная | A; B использовать в разделе «Комнаты» | Детализация §6.2 |
| Частые действия | Шесть мест на первом экране, начальный состав выбрать вместе | Дополнение UX, состав ещё не выбран |
| Параметры | Шаги / предустановки / «Применить», для лампы шаг 10 п.п. | Детализация базового управления, точность требуется согласовать |
| Возврат к картине | 45 с, настраиваемые 30/45/60 с | Внутри диапазона §2.2 |
| Первое касание | Только пробуждение до отпускания | Уточнение сценария §2.2 |
| Art Mode в первом MVP | 1 bpp с dithering; четыре уровня серого отдельным этапом, если приемлемо | Требует выбора: ТЗ оставляет уровни серого открытыми, текущий драйвер поддерживает только 1 bpp |
| Первичная настройка | Можно вынести ввод Wi-Fi и OAuth в телефонный поток | Способ в ТЗ не выбран; нужны отдельное согласование и проверка OAuth, это не принятая функция |
| Отклик пробуждения | Сначала измерить; не обещать время partial для холодного входа | Количественные критерии в §10 пока открыты |

**Не предлагаются без отдельного решения:** замена дисплея/платы,
постоянно включённый Wi-Fi ради мгновенного входа, отказ от Art Mode,
собственные LUT/напряжения, бессрочное питание EPD, перенос Reader/HA/dock в MVP.

Лимит 30 partial в V6 остаётся экспериментом диагностического стенда.
Он не подтверждает ресурс панели и не должен автоматически стать продуктовой
политикой очистки: Good Display рекомендует full clean после пяти partial.
Источник: [FAQ Good Display, п.29 и п.32](https://www.good-display.com/news/238.html).

## Следующая проверка до реализации всего UI

Собрать один вертикальный сценарий без расширения MVP:
**картина → реальное пробуждение → меню → одна команда Яндекса → подтверждённое
состояние → тайм-аут → та же картина → сон**.

Измерить отдельно:

1. Касание → первый видимый экран управления.
2. Пробуждение → готовность Wi-Fi/OAuth.
3. Нажатие → ответ API → подтверждённое состояние → готовая картинка.
4. Энергию сессии, ток ожидания с GT911 и ложные пробуждения.
5. Ghosting после повторных сессий Art/UI и фактическую длительность очистки.

Пределы отклика и автономности надо согласовать по этим измерениям — как
предусматривает §10 исходного ТЗ. Макеты подтверждают компоновку на 800×480,
но не эти аппаратные критерии.
